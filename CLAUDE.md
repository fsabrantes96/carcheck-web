# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

CarCheck Web: the front-end (Vite + React + TypeScript SPA) of a car marketplace where a buyer books a verified **inspector** (role `INSPECTOR`) to evaluate a car in person before buying. The back-end is [carcheck-api](../carcheck-api) (NestJS), whose `openapi.json` is the contract this repo generates its types from. It's a personal study project focused on clean backend↔frontend contracts. Code comments, UI text, error messages, commit messages, and PR descriptions are written in **Portuguese (pt-BR)**.

Done: tooling, generated API types, the API client with error handling by `code`, CI, and login and session (login, current user via `/auth/me`, protected routes, logout; sign-up comes later). Next up (README roadmap): listings, then inspectors and appointments. Stack decisions and their reasons are in [docs/decisions.md](docs/decisions.md); don't reopen them without the owner.

Known risks and their status (open, accepted, resolved) live in [docs/audit.md](docs/audit.md). Read it before designing, reviewing, or testing, and update it when a change resolves or introduces a risk.

## Commands

```bash
npm ci                 # install (see the npm 12 / allowScripts notes below)
npm run dev            # Vite on http://localhost:5173; /api/* is proxied to http://localhost:3000/* (prefix stripped)
npm run build          # vite build -> dist/
npm run preview        # serves dist/ with the same proxy
npm run lint           # eslint . (type-aware; no-floating-promises is an error; storage lock, see Architecture)
npm run typecheck      # tsc --noEmit for tsconfig.app.json and tsconfig.node.json
npm test               # vitest run (src/**/*.spec.{ts,tsx})
npm run test:watch     # vitest in watch mode
npx vitest run src/api/errors.spec.ts   # single file
npx vitest run -t "name of test"        # single test by name
npm run format         # prettier --write . (markdown is ignored)
npm run api:sync       # copies ../carcheck-api/openapi.json (or `-- <path>`) to api/openapi.json and regenerates src/api/schema.d.ts
npm run api:check      # regenerates into a temp file and fails if src/api/schema.d.ts differs (no back-end repo needed; runs in CI)
```

To run the app end to end, start the back-end first (see its README): API on `http://localhost:3000`.

**Node and npm versions** live only in `devEngines` in `package.json`: Node `^24.0.0` and npm `12.2.1` exact, both with `onFail: "error"`, so every `npm run` fails on another version (`EBADDEVENGINES`). Node 24 bundles npm 11; install the declared npm globally on top of it (`npm i -g npm@12.2.1`, check with `npm -v`). The CI reads both versions from there, so updating the local npm (or Node major) means updating `devEngines` in a `chore` commit first (and the versions quoted in this paragraph); never write a version in the workflow. Keep them in step with the back-end.

**Dependencies** are pinned to exact versions (no `^`/`~`; `.npmrc` has `save-exact=true`). npm 12 blocks dependency install scripts that aren't in `allowScripts` in `package.json`; there, `fsevents` (macOS-only watcher, optional dependency of Vite, runs `node-gyp`) is denied (`false`) on purpose. When a new dependency with an install script appears, `npm install-scripts ls` lists it: review what the script does and approve it pinned (`npm install-scripts approve <pkg>`) or deny it, never `--dangerously-allow-all-scripts`. Never run `npm audit fix --force`. TypeScript stays on 5.9.3 until openapi-typescript accepts TS 6 (risk 6); never force it with `overrides` or `--legacy-peer-deps`.

**Before `npm ci`, `npm install`, or anything else that deletes or rewrites `node_modules`:** list the node processes with their command lines (`Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Select-Object ProcessId, CreationDate, CommandLine`). If one belongs to this project (e.g. `npm run dev`, `vitest`), STOP and ask the user to stop it; never kill a user's process. On Windows a running process holds files in `node_modules` open and `npm ci` fails with EPERM halfway through.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on PRs to `main` with the same hardening as the back-end: job id `build` (the required status check name: never rename it, give it a `name:` or a matrix), `permissions: contents: read`, checkout with `persist-credentials: false`, actions pinned by the same commit SHAs as the back-end (version in a comment; risk 8), `timeout-minutes: 20`, `concurrency` cancelling the previous run, no npm cache (`package-manager-cache: false`). It installs npm from `devEngines` in `${{ runner.temp }}` (no step may run npm inside the project folder before npm 12.2.1 is installed: npm 11 enforces `devEngines` there), checks `npm -v`, runs `npm ci` with `NPM_CONFIG_STRICT_ALLOW_SCRIPTS=true`, requires `npm install-scripts ls --json` to be empty, runs `npm audit signatures`, then the permissions spec on its own (`./node_modules/.bin/vitest run --config src/claude/vitest.claude.config.ts`, failing on zero or skipped tests; see Testing), lint, typecheck, test, `api:check` and build.

## Architecture

- **ESM**, `"type": "module"`, `moduleResolution: "bundler"`: relative imports have **no** extension (unlike the back-end's NodeNext `.js`). `verbatimModuleSyntax` is on, so type-only imports use `import type`. `strict` and `noUncheckedIndexedAccess` are on.
- **Contract → types.** `api/openapi.json` is a committed copy of the back-end contract; `src/api/schema.d.ts` is generated from it by openapi-typescript and committed (both are generated: never edit by hand). **The back-end contract changed → run `npm run api:sync`, fix what `npm run typecheck` reports, and commit `api/openapi.json` and `src/api/schema.d.ts` in the same commit.** CI fails (`api:check`) if they drift apart. Always use the generated types (`paths`, `components['schemas'][...]`); never hand-write a type that duplicates a schema.
- **API client** ([src/api/client.ts](src/api/client.ts)): `createClient<paths>` from openapi-fetch (no axios), `baseUrl` `/api` resolved against the page origin (the back-end routes have no `/api` prefix; the Vite proxy strips it). `/auth/login` and `/auth/register` never carry the Bearer (`NO_AUTH_PATHS`), so their 401 is never a dropped session. **A new public route that can answer 401 (e.g. password recovery) goes into `NO_AUTH_PATHS`**; `client.spec.ts` fails when a contract operation without `security` documents a 401 and is missing from the list. The Bearer only goes to the origin of the client's `baseUrl`. A middleware adds `Authorization: Bearer <token>` when there is a token; a 401 on a request that carried the **current** token clears it and calls the callback registered with `setOnUnauthorized`. A 401 without a token (wrong password on login) triggers nothing. `unwrap(api.GET(...))` returns the data of a 2xx (`undefined` for a 204) or throws `ApiError` for any other HTTP status; use it in TanStack Query `queryFn`/`mutationFn`. **A network failure or an aborted request is not an `ApiError`**: fetch rejects with `TypeError`/`AbortError` and it passes through, so every error handler needs a branch for "not an `ApiError`" (show a generic "sem conexão" message, never crash). The middleware remembers the token each request carried (a `WeakMap` per `Request`) and compares the 401 against it, not against the header text. The client reads `globalThis.fetch` on each call on purpose (openapi-fetch would keep the reference from creation time and miss MSW).
- **Errors** ([src/api/errors.ts](src/api/errors.ts)): every back-end error carries a stable `code`. **Decide by `code` (with `hasCode(error, 'SOME_CODE')`), never by the pt-BR `message`**, which is for people and can change. Never compare `error.code` directly (`===`, `switch`): `ApiError.code` is typed `ErrorCode | 'UNKNOWN' | (string & {})`, so a typo or a renamed code would still compile, while `hasCode` only accepts codes of the contract. `hasCode(error, 'UNKNOWN')` is true only for a body without a code; an unknown code goes to the generic branch (the `else`/default, by HTTP status). With that open type, an unknown code is preserved and never breaks the screen (fall back on the HTTP status); a body without a code gets `UNKNOWN`, without a message gets a pt-BR default by status. `parseApiError` never throws (non-JSON, empty or missing body).
- **Open enums** ([src/api/enums.ts](src/api/enums.ts)): `AppointmentStatus`, `AppointmentAction`, `AppointmentActor` and `Role` (like `ErrorCode`) can grow on the back-end. Read them through `knownOr(value, LIST)`, which returns `UNKNOWN` for an unknown value, and give every UI `switch` an `UNKNOWN`/default branch. **An unknown enum value or code never breaks the screen.** The runtime lists fail the typecheck when the contract gains a value they lack, and `enums.spec.ts` checks them against `api/openapi.json`.
- **Storage only through [src/api/tokenStore.ts](src/api/tokenStore.ts).** It is the only module allowed to touch `sessionStorage`/`localStorage` (ESLint `no-restricted-globals` and `no-restricted-properties`, including `window.`/`globalThis.`/`self.` access, are errors everywhere else). Every access is inside `try/catch` (storage can throw); never log the token. The token moves to an httpOnly cookie before production (risk 1); don't spread token handling outside `tokenStore` and the client middleware.
- **Routes** live in [src/routes.tsx](src/routes.tsx) (`createBrowserRouter` in `main.tsx`, `createMemoryRouter` in tests). Pages in `src/pages/`, reusable components in `src/components/`, feature code in `src/features/<feature>/`.
- **Session** ([src/features/auth/](src/features/auth/)): the current user is the `['auth', 'me']` query (`currentUserQuery`: `GET /auth/me`, `retry: false`, `staleTime` 30 s), the only source of truth for the session (no copy in a Context); `useCurrentUser()` only fetches when `tokenStore` has a token. Protected routes are children of the `RequireAuth` layout in `routes.tsx`: without a token it redirects to `/login?from=<current path>`; with a token it waits for `/auth/me` (loading state, and a "Tentar de novo" screen on any other error, e.g. network or 5xx; a 401 drops the session instead). The login page reads `from` only through `safeRedirectPath` (internal paths only; anything else goes to `/`), removes the cached queries before saving the new token, then fetches the current user; its mutation has `gcTime: 0` because the password is in its `variables`. A dropped session (401 on a request that carried the current token) is wired by `registerSessionHandlers` (in `main.tsx` and `renderApp`): it clears the QueryClient and navigates to the login with `from` (staying on `/login` if already there). `useLogout` clears the token, navigates to `/login` and clears the cache even if the navigation fails; logout is front-only (risk 13).
- **Tailwind 4** through `@tailwindcss/vite` (`@import 'tailwindcss'` in `src/index.css`).

## Conventions

- Branches are `<type>/<name>`, with `<type>` one of `feat`, `fix`, `chore`, `test` or `docs`. Commits use Conventional Commits in Portuguese with a scope, e.g. `feat(auth): adiciona tela de login`.
- Commit messages are written to a file (UTF-8 **without BOM**) and passed with `git commit -F <file>`; keep the file outside the repo.
- `git add` only specific files, never `git add .` or `git add -A`.
- PRs follow [.github/pull_request_template.md](.github/pull_request_template.md): "O que mudou", "Como testar", and a checklist that includes the contract sync and the README roadmap.
- O agente nunca executa comandos que alteram o remoto, com uma única exceção: a skill /ship-pr, quando o usuário a aciona explicitamente. Merge, force push e remoção de branch remota são sempre do usuário.
- Never change anything in `../carcheck-api` from this repo; a back-end risk found here is reported to the user (and noted in this repo's audit).

A step that needs another spelling of a command gets a prompt (in the default mode); don't widen the list back to open wildcards. The grant only lasts for the turn in which the user types `/ship-pr`, so step 7 (after the approval) runs under `settings.json` and the permission mode. `git push` and `gh pr create` are deliberately left out, so each one still triggers a permission prompt, as a second lock, in the default mode; on 2026-11-15, the `ask` rules were approved without asking in auto mode; in the 2026-11-19 test (in the back-end) they asked for permission, as the docs say.   - **Syntax** (Claude Code docs): `*` matches any text, spaces included, and everything before the first `*` is literal, so an option needs either two rules (`git push --delete*` and `git push * --delete*`) or one without the space (`git push *--force*`, which also catches `"--force"`). A rule **must not end in `:*`**: a trailing `:*` means the same as ` *` (`Bash(ls:*)` = `Bash(ls *)`), so `git push * :*` would not match what it says. Deny beats ask beats allow and an allow can't carve an exception out of a deny; the docs don't say in so many words that this holds for a skill's `allowed-tools`, so don't count on it alone. Bash rules are matched case-sensitively, PowerShell rules case-insensitively.

## Testing

- **Vitest with globals** (`describe`, `it`, `expect`, `vi` without imports), jsdom by default (`// @vitest-environment node` at the top of a spec for pure Node). Use `vi.fn()`/`vi.spyOn`, never `jest`. Specs live next to the code as `src/**/*.spec.{ts,tsx}`.
- **Testing Library**: query by role and accessible name (`getByRole('heading', { name: 'CarCheck' })`), as the user sees it; `@testing-library/jest-dom` matchers are registered in [src/test/setup.ts](src/test/setup.ts).
- **MSW** simulates the API at the network level: the shared server in [src/test/server.ts](src/test/server.ts) starts with no handlers, each test registers its own with `server.use(http.get(...))`, and a request without a handler is an error (`onUnhandledFrame: 'error'`, the MSW 3 name). Never mock the API client or `fetch` directly. In tests, create the client with an absolute `baseUrl` (`createApiClient({ baseUrl: 'http://localhost/api' })`): Node's `Request` doesn't resolve relative URLs. Screen tests use `renderApp(path)` from [src/test/renderApp.tsx](src/test/renderApp.tsx) (same routes, QueryClient and `registerSessionHandlers` as `main.tsx`) and the contract-typed handlers and accounts in [src/test/api.ts](src/test/api.ts) (`API_URL` is the app client's `/api` on the jsdom origin). The setup waits for the `renderApp` QueryClients to stop fetching before resetting the MSW handlers ([src/test/pendingQueries.ts](src/test/pendingQueries.ts)); a test that leaves a request pending on purpose (`delay('infinite')` for a loading state) calls `queryClient.cancelQueries()` at the end.
- **Permissions spec config**: the permissions spec also has its own config, `src/claude/vitest.claude.config.ts` (`globals: true`, no `setupFiles`, doesn't import or extend `vitest.config.ts`, `include` with that spec only, `root` at the repository root computed from the config's location), which the CI runs in a separate step, so an exclude, alias or setup file in the test config can't take the spec out of CI or run code inside its Vitest process. It doesn't isolate the job, but no install script runs before that step: the `package.json` has no `preinstall`, `install`, `postinstall` or `prepare` script, and `allowScripts` approves no dependency script (risk 11, item G). The config uses Node APIs, so it is excluded from `tsconfig.app.json` and included in `tsconfig.node.json`. The spec also runs in `npm test`. The spec and this config are in the `Edit` deny and edited by hand by the user (see AI tooling).
- **Windows gotcha:** with the terminal in `c:\dev\carcheck-web` (lowercase drive), a package that imports `vitest` itself can get a second module instance (that's why the jest-dom matchers are registered through the global `expect` in the setup). If a matcher or mock seems ignored, check the drive letter before debugging the test.
- Test names are in pt-BR and describe behavior (`it('apaga o token e chama o onUnauthorized quando a requisição levou token')`). One behavior per `it`.
- **Tests are the specification.** When a test fails, fix the production code. Never edit, comment out, skip (`it.skip`/`it.todo`/`it.fails`) or loosen an existing test just to make it pass; if a test looks wrong, stop and explain why.
- Before adding a case, look in the module's existing spec file and extend it instead of duplicating cases.
- New behavior goes in two commits: `test(<scope>): ...` with the failing test, then `feat(<scope>): ...`. Bug fixes likewise: `test(<scope>): ...` failing, then `fix(<scope>): ...`.
- The storage lock is tested by the lint rule: `npm run lint` counts as its test.
