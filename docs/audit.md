# Riscos conhecidos do front

Leia antes de desenhar, revisar ou testar, e atualize quando uma mudança resolver ou introduzir um risco. Status: ABERTO (falta tratar), ACEITO (decisão consciente de não tratar agora), RESOLVIDO.

| # | Risco | Área | Status | Notas |
|---|---|---|---|---|
| 1 | Risco ALTO antes de produção. O JWT fica no `sessionStorage`: qualquer XSS no domínio do front lê o token. | Segurança / sessão | ACEITO até antes de produção (registrado em 2026-11-15) | Acesso só pelo `src/api/tokenStore.ts` (o ESLint proíbe `sessionStorage`/`localStorage` no resto do código). **Antes de produção**, migrar para cookie httpOnly + `SameSite`, o que exige mudança no back: login gravando o cookie, guard lendo o cookie em vez do header `Authorization`, logout que apaga o cookie e proteção contra CSRF. O `tokenStore` e o middleware do `src/api/client.ts` são os pontos a trocar no front. A trava do ESLint é contenção, não garantia: não pega apelidos (`const w = window; w.localStorage`), `document.defaultView.localStorage`, `Reflect.get`, `indexedDB`/`caches`/`document.cookie`, nem um `eslint-disable` dessas regras; revisão (pr-reviewer, security-reviewer) cobre o resto. Ao fazer o login: um 401 `INVALID_CREDENTIALS` num `POST /auth/login` feito com uma sessão ainda aberta derruba essa sessão (a requisição levou o token atual), e o logout/`onUnauthorized` precisa limpar o cache do TanStack Query (`queryClient.clear()`). |
| 2 | Risco MÉDIO (produto). As páginas públicas (anúncios, avaliadores) não têm SEO: é uma SPA, o HTML inicial é vazio e cada rota não tem título e meta próprios. | Produto / SEO | ACEITO (registrado em 2026-11-15) | Reavaliar quando as páginas públicas existirem: pré-renderização, SSR (ex.: React Router em modo framework) ou ao menos título e meta por rota. |
| 3 | Risco MÉDIO antes de produção. CORS em produção não está definido. O proxy do Vite (`/api` → `http://localhost:3000`) só existe em `npm run dev` e `npm run preview`; o `dist/` chama `/api` no mesmo domínio e não há nada servindo isso. | Infra / integração | ABERTO (registrado em 2026-11-15) | Decidir antes do primeiro deploy: mesmo domínio com proxy reverso para a API (sem CORS; combina com cookie httpOnly do risco 1) ou domínios separados com CORS restrito à origem do front no back e o `baseUrl` do `createApiClient` vindo de configuração de build. Se a API ficar em outra origem, conferir que o `Authorization` só vai para a origem da API (hoje o middleware põe o token em toda requisição do cliente, que só chama o próprio `baseUrl`). |
| 4 | Risco BAIXO (dependência). O `openapi-fetch` está em `0.x` (0.17.0): pela semver, uma versão minor pode quebrar a API. | Dependências | ACEITO (registrado em 2026-11-15) | Versão fixada sem `^`. Ao atualizar, ler o changelog e rodar a suíte inteira; os testes do `src/api/client.spec.ts` cobrem o middleware (`onRequest`/`onResponse`) e o formato `{ data, error, response }` que o `unwrap` usa. O cliente passa um `fetch` próprio (`globalThis.fetch` lido a cada chamada) porque o openapi-fetch guarda a referência do `fetch` global na criação. |
| 5 | Risco BAIXO, confirmado para o gerador atual. Risco 76 do back: campos anuláveis que apontam para enum nomeado (`endedBy` nas três variantes de agendamento) saem como `{ nullable: true, allOf: [{ $ref }] }` no OpenAPI 3.0.0, e um gerador estrito poderia tratar o campo como não anulável. | Contrato / tipos | RESOLVIDO para o openapi-typescript 7.13.0 (verificado em 2026-11-15) | O tipo gerado em `src/api/schema.d.ts` é `endedBy: components["schemas"]["AppointmentActor"] \| null;`, nas três variantes: correto. **Reabrir** se o front passar a validar respostas em runtime (ex.: zod gerado do contrato) ou trocar de gerador, e conferir de novo a cada atualização do openapi-typescript. Resultado a levar ao audit do back (risco 76), que não foi alterado por este repositório. |
| 6 | Risco BAIXO (ferramenta). O front usa TypeScript 5.9.3, uma versão atrás do back (6.0.3), até o openapi-typescript aceitar TypeScript 6 (a 7.13.0 pede `^5.x` como peer). O typescript-eslint 8.72.2 aceita `<6.1.0`. | Dependências / build | ACEITO (registrado em 2026-11-15) | Revisar a cada atualização do openapi-typescript (e do typescript-eslint): quando os dois aceitarem TypeScript 6, subir num commit `chore` próprio, rodando lint, typecheck, test, build e `api:check`. Não usar `overrides` nem `--legacy-peer-deps` para forçar. |
| 7 | Risco BAIXO (só em dev). `npm audit` acusa 7 vulnerabilidades `moderate`, todas do mesmo aviso: GHSA-g3hv-75wg-m249 (minimatch `>=7.0.0 <11.0.1`, negação de serviço por expansão de glob), via `@typescript-eslint/typescript-estree@8.72.2` → `minimatch@10.2.6`. | Dependências / dev | ACEITO (registrado em 2026-11-15, decisão do dono) | Só a ferramenta de lint usa, com globs nossos, localmente e no CI; não entra no bundle. O typescript-eslint 8.72.2 já é a versão mais recente, e a "correção" sugerida pelo `npm audit` (typescript-eslint 8.36.0) é um downgrade. Sem `overrides`. Revisar a cada atualização do typescript-eslint; nunca rodar `npm audit fix --force`. O CI roda `npm audit signatures`, não `npm audit`, então o aviso não derruba o CI. |
| 8 | Risco BAIXO (supply chain). As actions do CI estão fixadas pelo SHA do commit da tag, os mesmos do back (`actions/checkout` v7.0.1, `actions/setup-node` v7.1.0): uma tag movida não troca o código executado, mas o workflow também não recebe correções das actions sozinho. Sem cache do npm, cada run baixa as dependências de novo. | CI / dependências | ACEITO (registrado em 2026-11-15) | Mesmo tratamento do risco 79 do back: rever as actions a cada atualização do workflow e conferir um SHA novo com `gh api repos/actions/<repo>/git/ref/tags/<tag>`. |
| 9 | Risco MÉDIO antes de produção. Não há Content-Security-Policy. Com o token no `sessionStorage` (risco 1), uma CSP é a principal defesa em profundidade contra XSS. | Segurança / deploy | ABERTO (registrado em 2026-11-15) | Definir no deploy, de preferência por header: `default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'`, mais o `connect-src` da API se ela ficar em outra origem (risco 3). Achado da revisão de segurança da branch `chore/bootstrap`. |

O npm global que o CI instala (`npm install -g npm@<devEngines>`) não passa pelo `npm audit signatures`, que só cobre as dependências do projeto. | CI / dependências | ACEITO (registrado em 2026-11-15) | Igual ao back. Mitigações atuais: versão exata validada por regex `x.y.z`, `--ignore-scripts`, instalação fora da pasta do projeto. Opção (não implementada): conferir a integridade ou a atestação do pacote `npm` antes de instalar. Achado da revisão de segurança da branch `chore/bootstrap`. |
