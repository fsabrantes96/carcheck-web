# Riscos conhecidos do front

Leia antes de desenhar, revisar ou testar, e atualize quando uma mudança resolver ou introduzir um risco. Status: ABERTO (falta tratar), ACEITO (decisão consciente de não tratar agora), RESOLVIDO.

| 1 | Risco ALTO antes de produção. O JWT fica no `sessionStorage`: qualquer XSS no domínio do front lê o token. | Segurança / sessão | ACEITO até antes de produção (registrado em 2026-11-15) | Acesso só pelo `src/api/tokenStore.ts` (o ESLint proíbe `sessionStorage`/`localStorage` no resto do código). **Antes de produção**, migrar para cookie httpOnly + `SameSite`, o que exige mudança no back: login gravando o cookie, guard lendo o cookie em vez do header `Authorization`, logout que apaga o cookie e proteção contra CSRF. O `tokenStore` e o middleware do `src/api/client.ts` são os pontos a trocar no front. A trava do ESLint é contenção, não garantia: não pega apelidos (`const w = window; w.localStorage`), `document.defaultView.localStorage`, `Reflect.get`, `indexedDB`/`caches`/`document.cookie`, nem um `eslint-disable` dessas regras; revisão (pr-reviewer, security-reviewer) cobre o resto. Ao fazer o login: um 401 `INVALID_CREDENTIALS` num `POST /auth/login` feito com uma sessão ainda aberta derruba essa sessão (a requisição levou o token atual), e o logout/`onUnauthorized` precisa limpar o cache do TanStack Query (`queryClient.clear()`). |

| 11 | Risco BAIXO. A skill `/ship-pr` permite que o agente faça push da branch atual e abra a PR, a única exceção à regra de não alterar o remoto. As travas do lado do agente são parciais: as regras `deny`/`ask` do `.claude/settings.json` casam com o texto do comando, e a própria documentação do Claude Code diz que uma regra não barra o mesmo programa chamado de outra forma; e o `disable-model-invocation` impede o agente de carregar a skill sozinho, mas não de rodar `git push` por fora dela. Branch `chore/claude-permissions`. **O `.claude/settings.json` é idêntico ao do back** (em 2026-11-15, 290 `deny` e 72 `ask`, cada regra em `Bash(...)` e `PowerShell(...)`); mudar nos dois repositórios juntos. Mitigações: a skill só roda quando o usuário digita `/ship-pr`; `git push` e `gh pr create` ficam fora do `allowed-tools` e têm regra `ask`, então pedem permissão no modo padrão (no modo auto, não: ver o teste de 2026-11-15 abaixo); a skill para em qualquer verificação que falhe e espera aprovação explícita de título e descrição antes do push. **Proteção real no servidor** (conferida em 2026-11-15, só leitura): o ruleset `main-protection`, ativo e sem bypass, bloqueia na `main` a remoção, o force push (`non_fast_forward`) e o push direto (exige PR por squash, histórico linear e o status check `build`). Ele não protege as outras branches: force push ou remoção de uma branch de feature só são barrados pelas travas locais. **Fechado na segunda camada** (lista completa no `settings.json` e resumo no `CLAUDE.md`): push para a `main` por refspec (`HEAD:main`, `refs/heads/main`, `heads/main`, entre aspas), `--all`, `--mirror` e as abreviações que o git aceita; force por refspec `+` e por `"--force"`; remoção por `--delete`, `-d`, `--prune` e `:branch` (só para os tipos de branch do projeto e `refs/`); `gh api` com método ou corpo explícito, que permitiria merge de PR e edição do repositório por fora do deny de `gh pr merge`/`gh repo edit`; `gh` com flag antes do subcomando (`gh pr -R x merge`), o alias `gh issue new`, `gh alias` e os demais comandos `gh` de escrita conhecidos; extração do token (`gh auth token`, `--show-token`, `git credential`); `git grep -O`/`--op` e `--output`/`--ext-diff` em `git diff`/`log`/`show`. Viraram `ask`: toda opção global do git (`git -*`), `git config`, `git remote`, `git rebase -x`, `git submodule foreach`, `git bisect run`, `git subtree`, `git send-pack`, `git.exe`/`gh.exe`, `curl`/`wget`/`Invoke-RestMethod`/`Invoke-WebRequest` e os wrappers `env`, `exec`, `xargs`, `sh -c`, `bash -c`, `cmd /c`, `Invoke-Expression`, `Start-Process` e `wsl`. O `allowed-tools` da ship-pr passou a ter só os comandos exatos dos passos (antes, `git diff *`/`git grep *` aceitavam as opções acima e `npm test *` aceitava `npm test -- -u`); a liberação vale só no turno do `/ship-pr`. Ressalva: o `*` dos globs `"*.spec.ts"`/`"*.spec.tsx"` nas entradas de `git diff -w` e `git grep -c` também é curinga para o Claude Code, então essas entradas não são exatas (o `CLAUDE.md` e a skill dizem "sem curinga exceto o nome da branch", texto igual ao do back e impreciso nos dois); como o curinga fica depois do `--`, o git trata o que entrar ali como caminho, não como opção, mas falta confirmar se um redirecionamento (`> arquivo`) no meio do comando casaria com a regra (revisão de segurança de 2026-11-15; levar ao back). A documentação não diz com todas as letras se o deny vence o `allowed-tools` da skill. **Continua sem cobertura, e não dá para garantir só com regra de permissão**: caminho absoluto do `git`/`gh`; `GIT` em maiúsculas no Bash (o NTFS acha o executável, a regra de Bash diferencia maiúsculas; confirmado no teste do back) e, por dedução, `GH`; `pwsh -Command`, `node -e` e `& { ... }` no PowerShell; configuração que faz o git executar outro programa num comando liberado (`core.fsmonitor` no `git status`, `diff.external`, driver `diff.<x>.command` ou `textconv` no `git diff`), se já existir ou for gravada antes; comando montado por variável ou pelas variáveis `GIT_CONFIG_*` (`GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`); script que chama git por dentro (script do npm, hook, teste); alias ou configuração de remoto (`remote.<nome>.mirror`, `remote.<nome>.push`) que já exista ou seja gravada em `.git/config`, `~/.gitconfig` ou na config do `gh` com uma ferramenta de arquivo; flags curtas combinadas em outra ordem (`-vf`, `-ud`); concatenação ou escape no texto (`mai''n`, `\+x`); `:branch` com nome fora dos tipos do projeto (ex.: `':nao-existe'`), que cai em `ask` e não em `deny` (confirmado no teste do back); `git push --tags` (cai em `ask`); comandos `gh` de escrita fora da lista (é uma denylist, não um inventário); push que depende da branch atual (`git push` estando na `main`, barrado pelo ruleset). Não implementado, para decisão (igual ao back): deny de `Edit`/`Write` em `.git/config`, `.git/hooks/**`, `~/.gitconfig` e na config do `gh`; `ask` de `gh *`. **Teste de 2026-11-15** (feito no back, com o mesmo arquivo, no Bash e no PowerShell): as regras `deny` bloquearam todos os casos, inclusive no modo auto; as regras `ask` pediram permissão em todos os casos no modo padrão, mas no modo auto foram aprovadas sem perguntar. Portanto, no modo auto, a única barreira contra push ou PR não pedidos é a regra do `CLAUDE.md` (Conventions), e a `main` continua protegida pelo ruleset; tarefas que publicam (`/ship-pr`) devem rodar no modo padrão. **Teste repetido no front em 2026-11-15** (modo padrão, cada comando no Bash e no PowerShell): as regras `deny` bloquearam todos os casos nas duas ferramentas, e as regras `ask` pediram permissão. Os prefixos `& git` (PowerShell) e `command git` (Bash), antes listados como lacuna, foram testados com `git push --dry-run -f`/`--force` e bloqueados pelos `deny` de force push: testado, coberto. O modo auto não foi testado no front; como o arquivo é idêntico, vale o resultado do back. |
