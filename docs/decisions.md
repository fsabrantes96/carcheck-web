# Decisões

Stack e motivo de cada escolha. Mudar uma delas é decisão do dono do projeto.

| Escolha | Motivo |
| --- | --- |
| **Vite + React + TypeScript (SPA)** | Build rápido e simples para um app que fala com uma API separada. Sem SSR por enquanto (custo: SEO das páginas públicas, risco 2 do audit). |
| **React Router** (`createBrowserRouter`) | Roteamento padrão do ecossistema React. A tabela de rotas fica em `src/routes.tsx` e os testes usam `createMemoryRouter` com as mesmas rotas. |
| **Tailwind** (plugin `@tailwindcss/vite`) | Estilo direto no componente, sem CSS solto; o plugin do Vite dispensa PostCSS. |
| **TanStack Query** | Cache, loading e erro das chamadas sem estado global feito à mão. As `queryFn` usam `unwrap`, que lança `ApiError`. |
| **openapi-typescript + openapi-fetch** | Tipos gerados do `openapi.json` do back e cliente tipado por eles: mudança de contrato vira erro de tipo. Sem axios: o openapi-fetch usa o `fetch` nativo. |
| **Tipos e contrato commitados** (`api/openapi.json`, `src/api/schema.d.ts`) | O build e o CI não dependem do repositório do back; o `api:check` garante que os dois arquivos estão em sincronia. |
| **TypeScript 5.9.3** (o back usa 6.0.3) | O openapi-typescript 7.13.0 pede TypeScript `^5.x` como peer e o typescript-eslint aceita `<6.1.0`; o TypeScript 7 do template do Vite não funciona com nenhum dos dois. Risco 6 do audit. |
| **Token em `sessionStorage`, só pelo `src/api/tokenStore.ts`** | Temporário, para não exigir mudança no back agora. Concentrar o acesso num módulo deixa a troca por cookie httpOnly num lugar só (risco 1 do audit). O ESLint proíbe storage no resto do código. |
| **ESLint + typescript-eslint** (o back usa oxlint) | O front precisa dos plugins do ecossistema React (`react-hooks`, `react-refresh`) e da regra `no-restricted-globals`/`no-restricted-properties` que tranca o storage no `tokenStore.ts`, que o oxlint não cobre do mesmo jeito. As regras type-aware mantêm a do back: `no-floating-promises` como erro. |
| **Prettier com o `.prettierrc` do back** | Mesmo estilo nos dois repositórios (`singleQuote`, `trailingComma: all`). |
| **Vitest + Testing Library + MSW** | Mesmo runner do back; a Testing Library testa pelo que o usuário vê; o MSW simula a API na camada de rede, sem mockar o cliente. |
| **Proxy do Vite** (`/api` → `http://localhost:3000`, sem o prefixo) | Evita CORS em dev. Em produção ainda não está definido (risco 3 do audit). |
| **Usuário atual numa query do TanStack Query** (`src/features/auth/currentUser.ts`) | O `GET /auth/me` com a chave `['auth', 'me']` é a única fonte da verdade da sessão, lida pelo hook `useCurrentUser`. Sem cópia em Context. Só busca com token, sem nova tentativa automática (401 derruba a sessão no cliente, e para rede ou 5xx a tela oferece "Tentar de novo") e com `staleTime` de 30 s, para a rota protegida não buscar de novo o usuário que o login acabou de buscar. A rota protegida (`RequireAuth`) manda para `/login?from=<caminho atual>` sem token e mostra carregando enquanto o `/auth/me` não responde. Aprovado em 2026-11-16, branch `feat/login`. |
| **Login e cadastro sem Bearer** (`NO_AUTH_PATHS` no `src/api/client.ts`) | Com sessão aberta, o `POST /auth/login` levava o token atual e um 401 `INVALID_CREDENTIALS` era tratado como sessão expirada. Sem token enviado, o 401 cai no ramo "401 sem token não é sessão caindo": o token atual continua e o `onUnauthorized` não é chamado; a tela decide pelo `code`. A lista é tipada por `keyof paths`. Login sem nova tentativa automática (o back aceita 5 por minuto por IP) e com `gcTime: 0` na mutation, para a senha não ficar no `MutationCache`. O Bearer só vai para a origem do `baseUrl` do cliente. Mensagens por `code`; code desconhecido cai no status (400 vira a mensagem de validação). Aprovado em 2026-11-16, branch `feat/login`. |
| **`from` do login só como caminho interno** (`safeRedirectPath`) | Contra open redirect: só passa o que começa com `/`, sem `//` nem `/\`, sem `\` nem caractere de controle, sem esquema e na mesma origem depois do parse, e o caminho já normalizado também não pode começar com `//` (a revisão de segurança achou `/.//site.com`, `/a/..//site.com` e `/%2e//site.com`, que o `new URL` normaliza para `//site.com`; corrigido na mesma branch). O próprio login, em qualquer grafia que a rota aceite (`/LOGIN`, `/login/`, pelo `matchPath`), e qualquer outra coisa viram `/`. `/login` aberto já logado vai direto para o `from` validado. Aprovado em 2026-11-16, branch `feat/login`. |
| **Queda da sessão e logout só no front** (`registerSessionHandlers`, `useLogout`) | O back não tem logout nem revogação de token (risco 10 do back). O `onUnauthorized` limpa o cache e manda para o login com o `from`; já no login, navega para o mesmo caminho (sem aninhar o `from`), só para a tela renderizar de novo sem token; recebe o router por parâmetro, sem import circular com o `client.ts`. O logout apaga o token, navega para `/login` e só então chama `queryClient.clear()` (num `finally`, que roda mesmo se a navegação falhar). O token apagado continua válido no back até expirar (risco 13 do audit). Aprovado em 2026-11-16, branch `feat/login`. |
| **`devEngines` e `allowScripts` iguais aos do back** | Node `^24` e npm `12.2.1` exatos em todo lugar (local e CI); script de instalação de dependência só depois de revisado. |
